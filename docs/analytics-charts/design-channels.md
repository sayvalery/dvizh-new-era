# Каналы дистрибуции графиков: технические ограничения (email + соцсети)

**Дата:** 2026-08-12
**Статус:** research, кода нет
**Зачем:** ежемесячный дайджест «Итоги месяца» содержит 14–18 графиков. Сейчас каждый график — один SVG шириной 1080 px с текстом в кривых (79–154 КБ), и один и тот же файл уходит в три канала: статья на сайте, email-рассылка, посты в Telegram/VK. Переходим на генерацию из данных — нужно знать, какие ограничения накладывают почта и соцсети, потому что именно они диктуют требования к экспорту.

**Вне скоупа:** типы графиков, композиция, цветовые решения, выбор визуализации. Здесь только технические ограничения каналов.

### 1.2 Вердикт по SVG в почте

**Нельзя.** Не как основной формат, не как «попробуем, где-то сработает».

Обоснование в одном абзаце: главный клиент рынка (Gmail) не рендерит ни связанный SVG, ни inline SVG; Mail.ru не рендерит ни то, ни другое; по Яндекс.Почте проверяемых данных нет вообще, а «нет данных» в почте всегда трактуется как «не поддерживается»; Outlook на Word-движке (2007–2016) — тоже нет. То есть неподдерживающими оказываются именно те клиенты, где сидит российская b2b-аудитория.

**Безопасный дефолт для письма: PNG, отдаваемый по абсолютному `https://`-URL.** Не base64 (Gmail не умеет), не WebP (Gmail пересжимает в JPEG, Outlook не умеет), не SVG.

### 1.3 Ширина

- Отраслевой безопасный контейнер письма — **600 px**, допустимый диапазон 600–640 px; выше 640 растёт риск на Outlook Windows (Word-движок непредсказуем на нестандартных ширинах).
- Значит **ширина показа графика в письме = 600 px** (в одноколоночном письме с паддингами — 560–600 px).
- На мобильном письмо ресайзится: у картинки обязателен `style="width:100%; max-width:600px; height:auto;"`.

### 1.4 Retina / 2x

Механика: экспортируем файл в 2× от ширины показа и явно сжимаем его атрибутами.

```html
<img src="…/chart-approval-2026-05@2x.png"
     width="600" height="400"
     alt="…"
     style="width:100%; max-width:600px; height:auto; -ms-interpolation-mode:bicubic; display:block;">
```

- **Файл 1200 px, показ 600 px.** 3× не делать: рост веса без заметной выгоды.
- `width`/`height` **атрибутами** обязательны — Outlook на Windows масштабирует картинки по системному DPI и без явных атрибутов ломает раскладку; заодно это резервирует место при выключенных картинках.
- `-ms-interpolation-mode: bicubic` — устаревшее свойство IE, но именно оно спасает уменьшение картинки в старых Outlook/IE-движках, где по умолчанию используется nearest-neighbor (даёт «рваные» линии и текст при downscale). Свойство безвредно для остальных.
- Важное следствие: 2× **не** решает проблему читаемости. Он даёт резкость, но физический размер подписи на экране определяется шириной **показа** (600 px), а не шириной файла. Кегль — отдельное требование, см. §2.4.

### 1.5 Тёмная тема

Клиенты делятся на четыре группы поведения (сводка Mindbox + исследование EMAILMATRIX):

| Поведение | Клиенты | Что делает |
|---|---|---|
| Ничего не меняет | десктопные клиенты, **Яндекс.Почта web**, Gmail web | письмо как в светлой теме |
| Частичная инверсия | **Mail.ru**, Outlook.com, Gmail Android, **Яндекс.Почта mobile** | светлые фоны темнеют, тёмные элементы не трогаются |
| Полная инверсия | Gmail iOS, Outlook 2021 / Office 365 | инвертирует и светлое, и тёмное |
| Только обвязка | Apple Mail desktop | контент не трогает |

Официальная документация Mail.ru для разработчиков рассылок прямо говорит: письмо **перекрашивается** (подбирается фон, затем цвета границ, кнопок, текста), при этом **«цвет изображений не меняется»**; для управления перекраской предлагается `prefers-color-scheme`.

⚠️ Расхождение в источниках, которое надо знать: Mail.ru заявляет поддержку `prefers-color-scheme`, а caniemail на срезах 2020-10 и 2022-12 фиксирует `mail-ru: не поддерживается`. Трактовать как «ненадёжно, на это нельзя опираться».

Gmail (все платформы, срезы до 2022-12) `prefers-color-scheme` **не поддерживает вообще** — и `color-scheme` meta тоже нет. То есть CSS-механизмов управления тёмной темой в главном клиенте нет в принципе.

**Что из этого следует для графика — конкретно:**

1. **Прозрачный фон + тёмный текст = гарантированная поломка.** Клиент с инверсией сделает подложку письма тёмной, пиксели картинки не тронет (изображения не перекрашиваются) → тёмно-серые подписи осей окажутся на тёмном фоне. Это ровно та проблема, которая описана в задаче.
2. **Защита — непрозрачный светлый фон, запечённый в сам PNG.** Клиенты инвертируют CSS-цвета, но не трогают пиксели растровой картинки. Это единственная защита, которая работает во всех четырёх группах поведения и не требует поддержки CSS.
3. Побочный эффект: в тёмной теме светлый прямоугольник графика будет контрастировать с потемневшим фоном письма. Это **косметика, а не потеря читаемости** — приемлемая цена. Смягчается, если фон графика совпадает с фоном карточки (`#FBF9F6`/белый) и у графика есть собственные внутренние отступы, то есть он выглядит как намеренная светлая карточка.
4. **Не делать в v1** двойной экспорт (светлая/тёмная версия) и переключение по `prefers-color-scheme`: Gmail не поддерживает медиа-запрос, `<picture>` в Gmail/Outlook/Mail.ru вырезается — механизма доставки тёмной версии в основные клиенты просто нет.

### 1.6 Вес письма и обрезка Gmail (~102 КБ)

- Gmail обрезает письмо («Message clipped… View entire message») при превышении **~102 КБ**, и считается при этом **только размер HTML-части**: текст, теги, inline-CSS, URL картинок, трекинг-параметры, alt-тексты. Внешние картинки, загружаемые по URL, в этот вес **не входят**.
- Значит **14–18 графиков картинками по URL порог не нарушают.** Прикидка: 18 блоков × (URL с utm ~150 симв. + alt ~150 симв. + inline-стили ~200 симв.) ≈ 9 КБ. Плюс каркас письма. Целиться в **< 100 КБ HTML** с запасом.
- А вот **base64 порог убивает мгновенно**: один график в base64 — это ~80–200 КБ прямо в HTML. Уже второй график обрежет письмо. Это вторая независимая причина не использовать base64 (первая — Gmail его вообще не рендерит).
- Отдельно от обрезки: **суммарный вес загрузки**. Оценка для плоскоцветных графиков 1200 px: 40–90 КБ на PNG-24, 15–40 КБ при квантовании палитры (PNG-8, 32–64 цвета — для графиков этого достаточно). 18 графиков → **0.3–1.6 МБ** на письмо. Это не ломает доставку, но на мобильном интернете письмо будет догружаться долго. Практический ориентир: **≤ 60 КБ на график, ≤ 1 МБ картинок на письмо**; если не влезает — в письмо идут 4–6 главных графиков + ссылка «смотреть все» на статью (это продуктовое решение, но техника его подталкивает).

### 1.7 Выключенные картинки и доступность

- Outlook блокирует автозагрузку внешних картинок настройкой Trust Center; корпоративные администраторы блокируют массово. Достоверной цифры «сколько читателей с выключенными картинками» получить нельзя — Litmus прямо пишет, что точную долю не определить, и советует верстать так, будто она значима.
- Стандарты: WCAG 2.2 SC 1.1.1 (Non-text content) — у изображения обязателен текстовый эквивалент; SC 1.4.5 (Images of Text, AA) — изображений текста избегать. График как картинка в письме неизбежен, поэтому вывод обязан дублироваться живым текстом.
- **Что должно быть в `alt`** (сейчас там только название графика — это надо менять):
  - формула: **вывод + ключевые числа + период**, не название графика;
  - плохо: `Процент одобрения по регионам за май 2026`;
  - хорошо: `Одобрение в мае 2026: Москва 78 %, Петербург 74 %, Екатеринбург 71 %; разрыв между регионами сократился с 11 до 7 п.п.`;
  - длина ≤ ~150 символов — дальше клиенты и скринридеры обрезают; если данных больше, остальное уходит в подпись;
  - `alt` в письме **нельзя надёжно стилизовать** (шрифт, цвет, размер) — не рассчитывать на «красивый alt».
- **Живая подпись (caption) под каждым графиком обычным HTML-текстом** — обязательна. Один-два предложения с главным выводом и цифрой. Это единственный элемент, который одновременно: читается при выключенных картинках, читается скринридером, индексируется на сайте и переживает любую тёмную тему.

## 2. Соцсети

### 2.1 Telegram (главный канал)

**Что делает платформа с файлом:**

- При отправке «как фото» клиент ресайзит изображение в бокс из фиксированного набора: 90, 320, 800, **1280** (мобильные), **2560** (десктоп / режим HD), с JPEG-перекодированием (по замерам сообщества — качество ~87 %, хроматическая субдискретизация 4:2:0).
- Официальной таблицы «рекомендуемых размеров постов» Telegram не публикует. Отраслевая практика (несколько независимых гайдов 2026): **1280 px по длинной стороне** для обычной публикации, до 2560 — в HD-режиме.
- **Прозрачность теряется.** Отправка «как фото» = конвертация в JPEG, JPEG не поддерживает альфа-канал; в зависимости от конвертера прозрачные пиксели становятся **чёрными**. Прямые баг-репорты в tdesktop это подтверждают. → для Telegram непрозрачный фон не «желательно», а **обязательно**.
- Отправка «как файл» (документ) сохраняет PNG без сжатия, но в канале это выглядит вложением, а не полноразмерной картинкой в посте. Годится только как дополнение («скачать в полном качестве»), не как основной способ публикации.
- Лимиты Bot API (`sendPhoto`), если будет автопостинг: файл **≤ 10 МБ**, сумма ширины и высоты **≤ 10 000**, соотношение сторон **≤ 20**. С запасом.

**Практический вывод:** отдавать PNG с длинной стороной **ровно ≤ 1280** — тогда мобильный клиент не делает повторный ресайз, и деградация ограничивается одним JPEG-проходом. Отдавать 1080 (как сейчас) тоже безопасно с точки зрения ресайза, но это заведомо теряет 15 % линейного разрешения на десктопе.

**Минимальный набор пресетов для Telegram:** `1280×720` (16:9) и `1280×1280` (1:1). Вертикальные форматы (4:5, 1080×1350) Telegram не обрезает — он масштабирует по ширине, так что это не про кроп, а про то, сколько влезет по высоте.

### 2.2 VK

- **Официально** (vk.ru/faq18545): сумма высоты и ширины **≤ 14 000 px**, каждая сторона **≤ 8 192 px**. Рекомендуемых размеров для постов VK официально не публикует.
- **Практика** (SMM-гайды 2026, вторичные источники): пост 1080×1080, вертикальный 1000×1200 (5:6), минимум по заявлению VK 510×510 — но на практике мылит, ниже 1000 не спускаться. Загрузчик ограничивает 2160–2560 px по длинной стороне, JPEG 4:2:0, качество ~87 %.
- **Вывод:** файл Telegram-пресета (1280) подходит для VK без изменений. Отдельный VK-пресет в v1 не нужен.

### 2.3 LinkedIn

- Официальная рекомендация LinkedIn Help: **1200×627 px (1.91:1)** для одиночного изображения в посте; при ширине < 200 px картинка вырождается в мелкий thumbnail слева.
- **Для нашей аудитории канал нерелевантен:** LinkedIn заблокирован в РФ с 2016 года, b2b-аудитория застройщиков там практически отсутствует. Пресет **не делать**. Если понадобится — email-пресет (1200 px) отличается от 1200×627 только пропорцией.

### 2.4 Минимальный кегль: что переживает сжатие и ресайз

Ключевая мысль, которая переворачивает задачу: **читаемость определяется не пиксельной шириной файла, а логической шириной показа.** Файл 2560 px, показанный на 320 pt, читается ровно так же плохо, как файл 1080 px, показанный на 320 pt. 2× даёт резкость, не размер.

Формула: `кегль_в_файле ≥ минимально_читаемый_рендер × (ширина_канвы / ширина_показа)`

Опорные значения для «минимально читаемого»:
- Apple HIG: минимальный размер текста **11 pt**;
- Material Design: caption **12 sp**, «ниже 12 sp не опускаться для того, что нужно прочесть».

Расчёты (**оценка**; официальных констант ширины показа Telegram не публикует, взяты типичные измеряемые значения):

| Канал | Канва | Ширина показа | Коэффициент | Мин. кегль в файле |
|---|---|---|---|---|
| Telegram, телефон | 1280 | ~300–360 pt (экран 390–430 pt) | 3.6–4.2 | **≥ 40 px** (подписи), заголовок ≥ 56–64 px |
| Telegram, телефон | 1080 | ~300–360 pt | 3.0–3.6 | ≥ 36 px |
| Email | 1200 (2×) | 600 px | 2.0 | **≥ 24 px** (подписи), заголовок ≥ 32–36 px |
| Email на телефоне | 1200 (2×) | ~340–390 px | ~3.2 | ≥ 24 px даёт рендер ~7.5 px — **на пределе** |
| Сайт | SVG | 700–800 px | 1.0 | 14–16 CSS px |

**Отсюда главный технический вывод всего документа: один файл не может обслужить и почту, и Telegram, если соблюдать минимальный кегль.** В Telegram минимум ~40 px на канве 1280, в письме — 24 px на канве 1200. Это не разный ресайз одной картинки, это **разная плотность подписей**: значит функция экспорта должна перерисовывать график под пресет (менять кегль, отступы, при необходимости прореживать подписи), а не масштабировать один готовый рендер.

Заметка про email на телефоне: 24 px @1200 даёт ~7.5 px фактического рендера — ниже порога. Полностью решить это в одной картинке нельзя (клиент письма всё равно вписывает 600-px блок в 360-px экран). Приемлемый компромисс — кегль подписей 26–28 px @1200 и меньше подписей; радикальное решение (отдельный mobile-пресет письма) в v1 не нужно, потому что доставить его нечем: `<picture>` в Gmail/Outlook/Mail.ru не работает.

**Дополнительно — что именно ломает JPEG 4:2:0 в Telegram/VK:**
- **цветной тонкий текст** размывается сильнее всего (цветовая информация ужимается вдвое по обеим осям) → текст на графике только тёмно-нейтральный на светлом фоне, бренд-оранжевый — для заливок и акцентов, не для подписей;
- **hairline-линии 1 px** (сетка, оси) исчезают или превращаются в грязь → минимум **2 px** при канве 1280;
- мелкие оранжевые подписи на светлом фоне — худший случай из возможных.

### 2.5 Предел числа категорий на телефоне

Расчёт для канвы 1280, полезная ширина после полей ~1150 px, кегль подписи 40 px, средняя ширина глифа Inter ≈ 0.5–0.55 em ≈ 21 px/символ, минимальный зазор между подписями 24 px:

| Тип подписи | Ширина подписи | Шаг | Предел категорий |
|---|---|---|---|
| «Май», «Июн» (3 симв.) | ~63 px | ~87 px | **≤ 13**, комфортно **10–12** |
| «Январь» (6 симв.) | ~126 px | ~150 px | **≤ 7** |
| «Сбербанк» (8 симв.) | ~168 px | ~192 px | **≤ 6** |
| «Альфа-Банк» (10 симв.) | ~210 px | ~234 px | **≤ 4–5** |

То есть: **горизонтальный ряд подписей на телефоне выдерживает ~12 коротких меток или ~5–6 словесных.** Дальше подписи начинают либо накладываться, либо их приходится крутить/уменьшать — и то и другое даёт «кашу», о которой говорится в задаче.

Технические потолки на одну картинку для мобильного просмотра (**оценка**, выводится из кегля и площади):
- элементов легенды: **≤ 4**;
- числовых меток данных: **≤ 20**;
- если категорий больше предела — единственные технические выходы: подписи в строку (категории по вертикали), прореживание подписей (каждая 2-я/3-я), либо разбиение на два изображения. *Выбор конкретного решения — этап визуализации, здесь только фиксируем границу.*

## 3. Требования к экспорту — чек-лист

### 3.1 Пресеты (минимальный практичный набор — три)

| Пресет | Канва (px) | Показ | Формат | Мин. кегль подписи | Фон | Целевой вес |
|---|---|---|---|---|---|---|
| **`web`** | адаптив | 700–800 px | **SVG** (текст текстом, не кривыми) | 14–16 CSS px | прозрачный допустим | ≤ 30 КБ |
| **`email`** | **1200 × H** | 600 px (2×) | **PNG** | **≥ 24 px** (лучше 26–28), заголовок ≥ 32 | **непрозрачный** светлый | **≤ 60 КБ** |
| **`social`** | **1280 × H** (720 / 1280 / 1350 по высоте) | ~320 pt | **PNG** (Telegram сам сделает JPEG) | **≥ 40 px**, заголовок ≥ 56 | **непрозрачный** светлый | ≤ 400 КБ |

`social` покрывает и Telegram, и VK (1280 проходит оба загрузчика без повторного ресайза). LinkedIn-пресета нет — канал нерелевантен.

### 3.2 Чек-лист (по нему проверяем реализацию)

**Форматы**
- [ ] Для писем экспортируется **PNG**. SVG в письмо не отдаётся ни как основной формат, ни как fallback.
- [ ] Никакого **base64/data-URI** в письме (Gmail не рендерит + мгновенная обрезка на 102 КБ).
- [ ] Никакого **WebP/AVIF** в письме (Gmail пересжимает в JPEG, Outlook Windows не поддерживает).
- [ ] Никакого `<picture>`/`<source>` в письме (вырезается в Gmail, Outlook, Mail.ru).
- [ ] На сайте — SVG с настоящим текстом (не кривые): даёт доступность, поиск по странице и вес.

**Размеры**
- [ ] `email`: канва 1200 px, показ 600 px (ровно 2×).
- [ ] `social`: длинная сторона **ровно ≤ 1280 px**.
- [ ] Высота/пропорция задаётся пресетом явно; для `social` есть 16:9 и 1:1.
- [ ] Соотношение сторон ≤ 20:1, сумма сторон ≤ 10 000 (лимиты Telegram Bot API) — на практике всегда выполняется, но валидатор дешёвый.

**Типографика внутри графика**
- [ ] Минимальный кегль подписи в файле: **`email` ≥ 24 px @1200**, **`social` ≥ 40 px @1280**. Проверяется на экспорте, а не на глаз.
- [ ] Кегль задаётся **пресетом**, а не масштабированием одного рендера. Один и тот же PNG на почту и в Telegram — запрещено.
- [ ] Толщина осей и линий данных **≥ 2 px** при канве 1280 (иначе съест JPEG 4:2:0).
- [ ] Текст подписей — тёмный нейтральный на светлом. Бренд-оранжевый `#ff4d00` — только заливки/акценты, не подписи.
- [ ] Число элементов легенды ≤ 4; горизонтальных подписей категорий ≤ 12 (короткие) / ≤ 6 (словесные); меток данных ≤ 20. При превышении — экспорт предупреждает.

**Фон и тёмная тема**
- [ ] **Непрозрачный** фон запечён в PNG во всех растровых пресетах. Причины: (а) в Telegram альфа-канал теряется при конвертации в JPEG и может стать чёрным; (б) в почте инвертирующие клиенты затемняют подложку, но пиксели картинки не трогают → тёмный текст на прозрачном фоне становится нечитаемым.
- [ ] Фон графика = фон карточки письма/статьи (белый или `#FBF9F6`), у графика есть внутренние отступы — тогда светлый прямоугольник в тёмной теме читается как намеренная карточка.
- [ ] Тёмная версия графика и `prefers-color-scheme` в v1 **не делаются** (в Gmail механизма доставки нет).

**Вес**
- [ ] `email`: ≤ 60 КБ на график (квантование палитры PNG-8/32–64 цвета для плоскоцветных графиков), ≤ 1 МБ картинок на письмо.
- [ ] HTML письма < 100 КБ (порог обрезки Gmail ~102 КБ; считается только HTML-часть).

**Разметка в письме**
- [ ] `<img>` с явными атрибутами `width`/`height` (в единицах показа: 600 × H), плюс `style="width:100%; max-width:600px; height:auto; display:block;"`.
- [ ] `-ms-interpolation-mode: bicubic` в inline-стиле (качество downscale в Outlook/IE-движках).
- [ ] Абсолютные `https://`-URL картинок, стабильные версионируемые имена файлов (`chart-<slug>-<YYYY-MM>@2x.png`) — письмо не пересобирается, ссылка должна жить.

**Доступность / картинки выключены**
- [ ] `alt` = **вывод + ключевые числа + период**, ≤ ~150 символов. Название графика в `alt` — не принимается.
- [ ] Под каждым графиком — **живая текстовая подпись** (обычный HTML) с главным выводом и цифрой. Работает при выключенных картинках, в скринридере и в SEO.
- [ ] Декоративных графиков нет: если картинка не несёт данных, её нет.

**Проверяемость**
- [ ] Экспорт детерминирован: одинаковые данные → побайтово одинаковый файл (иначе нельзя диффить и кэшировать).
- [ ] Ручной прогон письма на живых ящиках **Gmail, Mail.ru, Яндекс.Почта, Outlook.com** в светлой и тёмной теме перед первой отправкой. Причина: caniemail не покрывает Яндекс вообще, а данные по Mail.ru — 2020–2023 годов; Litmus/Email on Acid российские клиенты тоже покрывают плохо.

## 4. Что можно НЕ делать в первой версии

**Можно спокойно пропустить (без ущерба):**

| Пропускаем | Почему это безопасно |
|---|---|
| LinkedIn-пресет | Канал заблокирован в РФ, аудитории застройщиков там нет. Понадобится — добавится за час. |
| Тёмные версии графиков и `prefers-color-scheme` | Доставить их в Gmail невозможно (нет поддержки медиа-запроса, `<picture>` вырезается). Непрозрачный светлый фон закрывает проблему читаемости во всех клиентах. |
| WebP/AVIF | Экономия веса не стоит риска: Gmail пересжимает, Outlook Windows не рендерит. PNG с квантованной палитрой даёт сопоставимый вес на плоскоцветных графиках. |
| Отдельный mobile-пресет письма | Доставлять нечем (`<picture>` не работает). Решается кеглем 26–28 px @1200. |
| 3× (1800 px) для писем | Заметной выгоды над 2× нет, вес растёт линейно. |
| Отдельный VK-пресет | Файл 1280 проходит VK без повторного ресайза. |
| Вертикальный/сторис-пресет (1080×1350, 1080×1920) | Telegram не кропает, масштабирует по ширине; вертикаль — вопрос композиции, не техники. |
| Автопостинг в Telegram/VK через API | Публикация ручная, лимиты Bot API с запасом. Ничего не блокирует. |
| Интерактивность (тултипы, зум) в письме | В почте невозможна в принципе. |
| «Отправка как файл» в Telegram для полного качества | Опция для отдельных запросов, не часть основного потока. |
| Инлайн-SVG на сайте вместо `<img src=".svg">` | Разница только в возможности CSS-стилизации; на читаемость и вес не влияет. |

**Пропускать нельзя ни в каком случае:**

1. **PNG для писем вместо SVG.** SVG не рендерится в Gmail и Mail.ru — это не деградация, а пустое место на месте графика.
2. **Непрозрачный фон во всех растровых пресетах.** Иначе: чёрный фон в Telegram (потеря альфы при JPEG) и нечитаемый тёмный текст в инвертирующих почтовых клиентах. Одно свойство закрывает две разные поломки.
3. **2× для письма (файл 1200 → показ 600).** Без него график мылит на всех современных экранах — это ровно та жалоба, с которой начинали.
4. **Разные пресеты для почты и Telegram — с разным кеглем, не просто разным ресайзом.** Один файл на все каналы физически не может соблюсти минимальный кегль в обоих (24 px @1200 против 40 px @1280). Это главный технический вывод.
5. **Минимальный кегль как проверяемое условие экспорта**: ≥ 24 px @1200 (email), ≥ 40 px @1280 (social).
6. **Линии и оси ≥ 2 px, подписи тёмным нейтральным на светлом.** JPEG 4:2:0 в Telegram/VK уничтожает тонкий цветной текст и hairline-сетку.
7. **`alt` с выводом и числами + живая текстовая подпись под графиком.** Картинки в почте блокируются массово; без этого письмо для части подписчиков пустое, а для скринридера — пустое всегда.
8. **Никакого base64 в письме.** Двойной блокер: Gmail не рендерит + обрезка на 102 КБ со второго графика.
9. **Явные `width`/`height` у `<img>` + абсолютные версионируемые URL.** Иначе Outlook ломает раскладку, а отправленное письмо со временем «облезает».
10. **Ручной прогон по Gmail / Mail.ru / Яндекс.Почта / Outlook.com в обеих темах перед первой рассылкой.** По Яндексу проверяемых данных нет вообще — это единственный способ их получить.

## Что здесь оценка, а не факт

Помечено явно, чтобы это не превратилось в «данные»:

1. **Ширина показа картинки в Telegram на телефоне (~300–360 pt).** Telegram не публикует констант вёрстки. Значение взято как типичное для клиентов на экранах 390–430 pt. Все выводы о минимальном кегле (§2.4) и пределе категорий (§2.5) наследуют эту неточность — но направление вывода устойчиво: даже при 400 pt показа минимальный кегль на канве 1280 остаётся ~35 px, то есть текущие 1080-px графики с мелкими подписями всё равно нечитаемы.
2. **Вес PNG (40–90 КБ / 15–40 КБ с квантованием).** Оценка для плоскоцветной графики; реальные цифры получатся только на первом экспорте.
3. **Пределы числа категорий.** Арифметика от кегля и средней ширины глифа Inter (0.5–0.55 em), а не результат тестирования.
4. **Данные caniemail по Mail.ru — срезы 2020–2023**, по **Яндекс.Почте данных нет вообще**. Обе позиции требуют ручной проверки на живых ящиках. Для Mail.ru есть прямое расхождение: официальная документация заявляет поддержку `prefers-color-scheme`, caniemail фиксирует её отсутствие.
5. **Рекомендованные размеры постов Telegram и VK** — отраслевая практика из вторичных источников; официальных таблиц у платформ нет. Официальны только жёсткие лимиты (Bot API, VK FAQ).
