## Зафиксированная модель веток (главное решение)

| Ветка | Роль | Кто трогает | Куда видно |
|-------|------|-------------|------------|
| **`main`** | **ПРОД.** Деплой (кнопка «Опубликовать» в CMS) собирает **из `main`**. | Только промоут `dev→main` (Valery / скилл по команде «выкатить в прод») | **dvizh.io** (прод) |
| **`dev`** | Стейджинг/превью. Дизайнеры ломают свободно. | Все мержат сюда (скилл `sync`, Режим 2) | preview.dvizh.cc |
| `valery-sayfullin`, `anastasia-sheveleva`, `<533va→имя>` | Личные ветки | каждый сам, ответвляются **от `dev`** | — |

> **Домены (миграция .cc → .io).** Сейчас прод-сайт живёт на тестовом домене **dvizh.cc**, переезжает на основной **dvizh.io**. Превью (`dev`) остаётся на **preview.dvizh.cc**. Это отдельный пласт работ (DNS, nginx, CMS-домен admin.dvizh.io?, деиндексация .cc) — пересекается с прошлым контекстом «запуск dvizh.io». Связь с деплоем — см. «Открытые вопросы» (деплой на .io через CI/Actions).

**Ключевые правила:**
- Мерж в `dev` → попадает **только на preview**, в прод сам по себе НЕ идёт.
- **Выкатка в прод** = отдельное осознанное действие: промоут `dev→main` (мерж + push) → затем деплой из `main`. Триггер — явная команда **«выкатить в прод»**, гейт по пользователю (Valery).
- **Контент-публикация маркетолога** (кнопка «Опубликовать» без промоута) безопасна: пересобирает неизменный `main` + свежий контент из CMS. Эксперименты из `dev` в прод не утекают.

### Почему так (а не «оставить как есть»)
Сейчас деплой собирает из `dev`, а `dev` — песочница. Значит любая контент-публикация маркетолога выкатывает на прод весь текущий код `dev`, включая недоделанные эксперименты. Модель «main = прод» закрывает эту дыру и совпадает с ожиданиями разработчиков (main = продакшн). Откат прода (5 версий на VPS) от этого не зависит и продолжает работать.

## Бэкапы базы (новая инфраструктура, решено 2026-06-18)

**Принцип:** дампы базы в git НЕ кладём (раздувание истории + PII/секреты). Место — отдельная папка вне репозитория. `*.sql` уже в `.gitignore`. Уже существует ручная папка `~/dvizh-backups/<метка>/` со снимками (`dvizh-db.dump` ~2 МБ + `cms-media.tar.gz` ~220 МБ) — её ручные «вехи» не трогаем.

**Текущее состояние:** контейнер `dvizh-new-era-postgres-1` (postgres:16, БД `dvizh`, юзер `dvizh`), бэкапы делались вручную, скрипта нет, ротации нет, копия только на MacBook.

**Решения:**
- **Кадэнс:** авто перед каждым деплоем в прод + раз в день (LaunchAgent).
- **Где:** локально (`~/dvizh-backups/auto/`) + копия на Ubuntu VPS (rsync).
- **Что бэкапим:** всю базу (она маленькая, ~2 МБ — карвить отдельные таблицы смысла нет). НО критичные данные = **входящие заявки (`form_submissions`)**: статьи и контент по сути продублированы в последнем деплое и в CMS, а лиды живут ТОЛЬКО в базе. Поэтому лиды защищаем отдельно (см. ниже).

**⚠️ Защита от «обнуления» (ключевое замечание Valery):** наивная ротация «храним 5, перезаписываем по кругу» опасна — если база потёрлась/опустела, за 5 дней все бэкапы станут копиями пустой базы, и мы тихо потеряем всё. Поэтому:
- **Многоуровневое хранение (GFS), а не плоское N:** напр. 7 ежедневных + 4 еженедельных + 6 месячных. Даже если свежие бэкапы испорчены, остаётся старый заведомо хороший.
- **Sanity-check перед ротацией:** считать число строк `form_submissions` (и общий размер дампа) в новом бэкапе. Если оно **меньше**, чем в последнем хорошем, или дамп подозрительно мал → **не удалять старые** и **поднять тревогу** (Telegram, см. «Вне скоупа»). Молча не ротируем.
- **Append-only экспорт лидов:** отдельно дампить `form_submissions` в накопительный CSV/таблицу, которая **никогда не обнуляется ротацией** — последний рубеж для самых ценных данных.

**Новый скрипт `scripts/backup-db.sh`:**
- Дамп базы (~2 МБ): `docker exec dvizh-new-era-postgres-1 pg_dump -U dvizh -Fc dvizh` → `~/dvizh-backups/auto/<дата-время>/dvizh-db.dump`. На оба триггера.
- Медиа (~220 МБ): **инкрементальный rsync** (не полный tar каждый раз). Полный `cms-media.tar.gz` — реже (перед деплоем / еженедельно), отдельная ротация.
- Применить GFS-ротацию + sanity-check + alert (выше).
- **Копия на VPS:** rsync `~/dvizh-backups/auto/` → VPS (напр. `/var/backups/dvizh/`). ⚠️ В базе PII лидов — каталог только root, НЕ отдавать через nginx.

**Интеграция с деплоем:** вызвать `backup-db.sh` в начале `build-site.sh` (после проверки CMS, до сборки) — снимок-страховка перед любым изменением прода.

**Расписание:** LaunchAgent `com.dvizh.dbbackup` (по образцу `com.dvizh.autostart` / `com.dvizh.devserver`), ежедневно.

**Восстановление:** `docs/DEPLOY.md` — заменить ссылку на старый `dvizh_dump.sql` на инструкцию из `~/dvizh-backups/auto/<последний>/dvizh-db.dump` через `pg_restore` (формат `-Fc`).

Туда же — алерты бэкапов (sanity-check не прошёл). Заготовка уже есть: в `build-site.sh` закомментированы `notify()`-хуки на Telegram (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`).
- **🔴 Статус-пейдж / дашборд (отдельная задача, обсудить отдельно).** Небольшая страница за авторизацией (возможно — страница прямо в Payload CMS, если так можно) с состоянием системы: когда сделан последний бэкап, когда прошла проверка форм, всё ли идёт, логи этих проверок, количество заявок и т.п. По сути — визуализация того же, что гоняем в Telegram. Маркетинг может добавить хотелки. **Требует отдельного обсуждения с Valery** перед проектированием.
- Серверное ограничение промоута/пуша в `main` по **конкретным пользователям** (GitLab Protected Branches — free/CE по ролям, по именам — Premium/EE). Деплой-бот CMS позже — Project Access Token только на чтение `main`.
- Полноценный `.gitlab-ci.yml` (CI) — может слиться с вопросом 1 (деплой через CI).
- Миграция доменов `.cc → .io` (DNS, nginx, деиндексация .cc) — отдельный пласт, пересекается с «запуск dvizh.io».

## Риски и ограничения
- **Порядок Фазы 3** (промоут до смены `SOURCE_BRANCH`) — иначе откат сайта на март.
- `validate-build.sh` (порог 80% страниц) НЕ ловит выкатку «старого, но полного» `main` — не полагаться на него как на защиту от подвоха №1.
- Простой фикс коллизии оставляет окно в несколько секунд, когда preview на `main` — принято осознанно.
- Секреты (`.env.deploy`, `.env.prod`) провижинятся на сервере вне гита — при новом клоне на сервере их нужно положить отдельно.
- Наивная ротация бэкапов может «обнулить» все копии — закрыто GFS + sanity-check (см. «Бэкапы базы»).

## Действия на стороне пользователя (не автоматизируется)
1. Сменить пароль админки CMS.
2. Создать в GitLab проект + Personal Access Token, дать URL и группу.
3. Подтвердить, кого ставим Maintainer на `main` (для protected branches).
4. Финально уточнить у CTO формулировку по деплою (ожидается: вебхук на push в `main` = наша логика; не блокирует старт).
