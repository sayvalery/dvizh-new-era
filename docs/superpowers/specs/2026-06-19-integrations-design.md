## Контекст и цель
Интеграции настраиваются **маркетингом самостоятельно в админке (Payload)**, без участия разработки. Два независимых типа с РАЗНОЙ механикой — не смешивать.

Связано: [[integrations-and-leads]] (память), деплой-из-master ([[gitlab-migration-context]] Фаза 3) гарантирует чистую развязку код↔данные, мониторинг ([[monitoring-and-ci-todo]]) страхует «чтобы не упала».

## Тип A — маршрутизация заявок (данные, реальное время)

**Поток (надёжность — главное требование «чтобы не упала»):**
1. Форма → POST `/api/form-submissions` → **сохранение в CMS (Postgres) — единственный обязательный шаг.** Сразу ответ пользователю «Спасибо».
2. **Затем асинхронно** (server-side `afterChange`-хук Payload) рассылка: Telegram-лид + Albato + доп. вебхуки по пресету.
3. Каждый внешний вызов в `try/catch` — **его падение НЕ роняет заявку**. Лид уже в базе, не потерян. Сбои логируются + видимы (статус доставки / алерт).

**Маршрутизация (v1 — по пресету):**
- Глобально: **все формы → Albato** (одно поле webhook-URL). Albato берёт на себя ретраи/роутинг к нижестоящим сервисам.
- Правила: строки `{ пресет (demo/lead/research/subscribe), доп. webhook-URL, включён }`. Пример: `subscribe` → доп. вебхук рассыльщика.
- Telegram-лиды: **один канал** для всех (v1). Доп. маршрутизация — это про вебхуки, не про Telegram.

**Конфиг (Payload):** global/коллекция «Интеграции заявок» — { Albato URL, Telegram (бот/чат), правила[] }. Редактирует маркетинг (роль).

**v2 (потом):** матчинг по странице/источнику; per-preset Telegram; ретраи/наглядный статус доставки на самой заявке.

## Тип B — скрипты на страницы (пиксели/теги, build-time)

**Модель — коллекция «Скрипты страниц»**, повторяемые ИМЕНОВАННЫЕ записи:

| Поле | Что |
|------|-----|
| Название | «Яндекс.Метрика», «Google Tag» — для себя |
| Код | СЫРОЙ сниппет (маркетинг вставляет готовый из своего сервиса; поля «тип» НЕТ, известные интеграции не поддерживаем) |
| Где показывать | мультивыбор ГРУПП: весь сайт / главная / блог / глоссарий / кейсы / исследования / видео / продуктовые (конкретная страница — v2) |
| Куда | `<head>` / конец `<body>` |
| Включён | тумблер |

**Механика:** сайт статический (SSG) → скрипт появляется **после пересборки** («Опубликовать»). Вариант «сборочный» принят. На сборке layout по группе страницы вставляет подходящие включённые сниппеты.

**Валидация/защита:**
- «Пер-полевая валидация» удовлетворена структурно: каждая интеграция = отдельная именованная запись (не один блоб), включается/выключается, видно какая сломала.
- Базовая проверка при сохранении + **build-time страховка**: кривой код → сборка падает на валидации → симлинк не переключается → **старый сайт остаётся живым** (откат 5 версий). В прод сломанное не уедет.

## Зависимости и принципы
- **Развязка код↔данные:** код в git (dev/master), данные (статьи, пиксели, правила) — в CMS/Postgres. Конфликта в git нет (пиксель = запись в БД). Чистая развязка прода гарантируется деплоем **из master** (Фаза 3): публикация маркетинга = пересборка из стабильного master + свежие данные, эксперименты dev не утекают.
- **CMS одна на всех** (не дев/прод раздельно) → тумблер «включён»/черновик-публикация Payload, чтобы запись не «протекла» до готовности.
- Реализация — отдельным заходом; Тип A (хук) и Тип B (коллекция + инъекция на сборке) независимы.
