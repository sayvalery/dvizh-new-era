# Sync — Синхронизация и публикация

Скилл управляет ветками в двухуровневой модели:

```
main  ← ПРОД. Деплой собирает из main. Обновляется ТОЛЬКО промоутом dev→main (Valery, по команде «выкатить в прод»)
dev   ← стейджинг/превью, все мерджат сюда (preview.dvizh.cc)
  ├── valery-sayfullin
  ├── anastasia-sheveleva
  └── <личные ветки>     ← ответвляются от dev
```

- **`main` = прод.** Деплой пересобирает сайт **из `main`**. Единственный путь в прод — осознанный промоут `dev→main` (Режим 3).
- **`dev` = стейджинг.** Мерж сюда (Режим 2) попадает **только на preview.dvizh.cc**, в прод сам по себе НЕ идёт.
- **Личные ветки** — от `dev`, постоянные.

> ⚠️ **Сейчас деплой ФАКТИЧЕСКИ собирает из `dev`.** Переключение на `main` — pending (Фаза 3 миграции в GitLab, `docs/superpowers/specs/2026-06-18-gitlab-migration-design.md`). Модель «main = прод» — целевая. До переключения промоут `dev→main` ещё не выкатывает в прод сам по себе, но порядок и гейты соблюдаем уже сейчас.

## Определение пользователя

Получи имя из git:
```bash
git config user.name
```

Нормализуй в имя ветки: lowercase, пробелы → дефисы, убрать спецсимволы.
Пример: `Valery Sayfullin` → `valery-sayfullin`

## Режим 1: Начало работы

Вызывай когда пользователь начинает работу или в начале сессии.

### Шаги

1. Определи пользователя (git user.name)
2. Получи свежее состояние:
   ```bash
   git fetch origin
   ```
3. Проверь есть ли ветка пользователя (`git branch --list <имя>`)
4. Если ветки нет — создай от свежего dev:
   ```bash
   git checkout dev && git pull origin dev && git checkout -b <имя>
   ```
5. Если ветка есть — переключись и обнови поверх dev (rebase, не merge!):
   ```bash
   git checkout <имя>
   git pull origin <имя> --rebase 2>/dev/null || true
   git rebase origin/dev
   ```
6. Если при rebase возникли конфликты — запусти визард конфликтов (см. ниже), затем `git rebase --continue`

### Почему rebase, а не merge

`git pull origin dev --no-edit` создаёт мусорные merge-коммиты в ветке пользователя («Merge branch dev into stacy»). Rebase ставит коммиты пользователя поверх свежего dev — история остаётся чистой и линейной.

### Вывод

```
🔄 ═══════════════════════════════════════
   SYNC · НАЧАЛО РАБОТЫ
═══════════════════════════════════════
👤 Пользователь ................ Valery Sayfullin
🌿 Ветка ....................... valery-sayfullin
📥 Dev ......................... ✅ Синхронизирован
═══════════════════════════════════════
   Готово! Работай в своей ветке.
   Когда закончишь — скажи «опубликуй»
═══════════════════════════════════════
```

## Режим 2: Публикация в dev

Вызывай когда пользователь говорит: «опубликуй», «мерж», «в dev», «готово, публикуй», «sync publish».

> Мерж в `dev` попадает **только на preview.dvizh.cc**, в прод сам по себе НЕ идёт. Чтобы выкатить в прод — отдельная команда «выкатить в прод» (Режим 3).

### Шаги

1. Проверь что все изменения закоммичены. Если нет — предложи закоммитить
1.5. **Спроси пользователя: «Прогнать typo-fix перед мержем? (да/нет)»**
   - На «да» — вызови скилл `typo-fix` (он сам определит скоуп по git-diff, покажет правки, спросит подтверждение).
   - Если скилл применил правки — в рабочем дереве появятся незакоммиченные изменения. Предложи закоммитить их перед мержем (`git commit -m "typo: NBSP + ё→е"`).
   - На «нет» / если правок нет — продолжай мерж.
2. Запомни имя ветки пользователя
3. Получи свежий dev:
   ```bash
   git fetch origin dev
   git checkout dev
   git pull origin dev
   ```
4. Мержи ветку пользователя:
   ```bash
   git merge <ветка> --no-edit
   ```
5. Если конфликтов нет:
   ```bash
   git push origin dev
   ```
6. Если конфликты — запусти визард конфликтов, потом push
7. После успешного мержа — вернись на ветку пользователя и обнови:
   ```bash
   git checkout <ветка>
   git rebase origin/dev
   ```

### Вывод при успехе

```
🚀 ═══════════════════════════════════════
   SYNC · ПУБЛИКАЦИЯ В DEV
═══════════════════════════════════════
👤 Пользователь ................ Valery Sayfullin
🌿 Ветка ....................... valery-sayfullin → dev
📦 Коммиты ..................... 3 коммита влиты
🔄 Push ........................ ✅ Отправлено в dev
═══════════════════════════════════════
   Опубликовано в dev!
   Проверь на preview.dvizh.cc
═══════════════════════════════════════
```

## Режим 3: Выкатка в прод — промоут dev→main (ЕДИНСТВЕННЫЙ путь в прод)

Вызывай когда пользователь говорит: «выкатить в прод», «в прод», «промоут в main», «мерж в main», «опубликуй в прод».

Это **единственный** способ обновить прод. Деплой собирает из `main` (целевая модель; сейчас фактически из `dev` — Фаза 3 pending), поэтому код попадает в прод только через явный промоут `dev→main`.

### Проверка доступа

Получи имя пользователя из `git config user.name`.

Если НЕ содержит «valery» (регистронезависимо):
```
⛔ ═══════════════════════════════════════
   Выкатка в прод (промоут dev→main) доступна только Valery.
   Используй «опубликуй» для мержа в dev (попадёт на preview).
═══════════════════════════════════════
```
Прекрати выполнение.

> Серверный гейт по конкретному пользователю (GitLab Protected Branches) — pending. Пока ограничение держится этим скиллом.

Если Valery — предупреди:
```
⚠️ Выкатка в прод (промоут dev→main)
   dev смержится в main и попадёт в прод (deploy из main).
   Убедись, что dev стабилен и проверен на preview.dvizh.cc.

   Промоутить dev→main? (да/нет)
```

Если подтвердил:
```bash
git checkout main && git pull origin main
git merge dev --no-edit
git push origin main
git checkout dev
```

После промоута — запусти деплой из `main` (`bash scripts/build-site.sh` или кнопка «Опубликовать» в CMS), либо предупреди пользователя, что нужно задеплоить.

> **Контент-публикация маркетолога** (кнопка «Опубликовать» без промоута) безопасна: пересобирает неизменный `main` со свежим контентом из CMS. Эксперименты из `dev` в прод НЕ утекают — для этого нужен явный промоут выше.

## Визард конфликтов

Когда merge или rebase даёт конфликты — НЕ решай молча. Проведи пользователя через каждый файл.

### Для каждого конфликтного файла:

1. Покажи понятное описание:
```
⚠️ Конфликт в файле: src/components/ui/Form.astro

📄 Версия из dev (коллега, 25 фев 14:30):
   Изменён стиль кнопки — добавлен hover-эффект

📄 Твоя версия (26 фев 10:15):
   Добавлено новое поле «телефон»

Что делаем?
  1) Оставить версию из dev (коллеги)
  2) Оставить твою версию
  3) Объединить оба изменения (я попробую автоматически)
```

2. Дождись ответа пользователя
3. Примени выбор
4. Переходи к следующему файлу

### Определение дат и авторов

Для показа информации о конфликтующих изменениях:
```bash
git log origin/dev --oneline -1 -- <файл>
git log <ветка> --oneline -1 -- <файл>
```

### После разрешения всех конфликтов

Для merge:
```bash
git add . && git commit --no-edit
```

Для rebase:
```bash
git add . && git rebase --continue
```

Продолжи с push как в обычном режиме.

## Важно

- НИКОГДА не делай force push в dev или main
- Force push в ветку пользователя допустим ТОЛЬКО после rebase (и это нормально)
- НИКОГДА не удаляй чужие ветки
- При сомнениях — спрашивай пользователя
- Ветка пользователя НЕ удаляется после мержа — она постоянная
- `main` — только через промоут `dev→main` (Режим 3, гейт по Valery). Это единственный путь в прод
- Мерж в `dev` (Режим 2) → только preview, в прод сам по себе НЕ идёт

## Guardrail-хук (опционально)

Перед push можно прогонять машинный чек-лист `scripts/audit.sh` (запрещённые импорты, dev-утечки в dist, хардкод-hex, битые ссылки) через git-хук `.githooks/pre-push`. По умолчанию **не активирован**. Включить однократно из корня репозитория:

```bash
git config core.hooksPath .githooks   # активировать
git config --unset core.hooksPath      # отключить
```

При FAIL push блокируется; разовый обход — `git push --no-verify`. Если хук активен, push в Режимах 2/3 может остановиться на аудите — сообщи пользователю причину, не обходи молча.
